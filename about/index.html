Why I make PWAs

Plain talk. Good bits and caveats. No sales pitch.

I’m ambr3. I make Seclusa apps as Progressive Web Apps (PWAs). Fancy name, simple idea: a website you can install, that can work offline, and that runs inside your browser like other websites do.

I care about privacy first, then security. PWAs help with both when you build them the hard way: data on your device, no accounts, no trackers. That is usually better for privacy than a typical store app. It is not automatically safer than every native app forever. I will say the bad parts too.

More private

Privacy means: who can see your stuff, and does anyone need to?

Your data stays on your phone

The apps keep notes, calendar events, blood-pressure readings, game scores and so on in browser storage on your device (things like IndexedDB). They do not upload that to me. Weather is the main exception: it asks Open-Meteo for forecasts, and the app says so.

No account means no login for me to sell, and no cloud copy of your life sitting on a company server by default.

No ads, no spy codes

A lot of store apps ship with ad or analytics kits. Those can read a phone advertising ID (IDFA on iPhone, GAID on Android) and help follow you across apps. Normal websites and PWAs cannot read those IDs.

They can still track you with cookies or sneaky scripts — if the maker adds them. Seclusa does not. No ads. No analytics. No third-party script or font CDNs that report your visit. If I do not load someone else’s code, there is no someone else to phone home to.

You can still wipe it

Because it is a website under the hood, your browser’s normal tools still work: clear site data, block trackers, revoke permissions. To really remove an installed PWA, clear that site’s data / uninstall it. That is clearer than hoping a store app and every kit inside it went quiet.

More secure

Security means: if something goes wrong, how much damage can the code do?

Stuck in its own box

A PWA only “owns” its own website address (its origin). Under the browser’s same-origin policy, its storage and permissions stay in that box. Bad script in the app can mess with that app’s data. It does not get free run of your whole phone, your files, or your other apps — a smaller blast radius than native code that already has lots of permissions.

HTTPS, and locked doors

The offline bit uses a service worker. Browsers only allow that on secure pages (HTTPS). That stops a random café Wi‑Fi attacker from easily slipping in a fake offline shell. See also Chromium’s Service Worker Security FAQ.

Seclusa apps also use strict Content-Security-Policy and Permissions-Policy rules. In plain English: the page is told “no camera, no mic, no payment APIs” and “only load my own scripts.”

Ask one thing at a time

If a web app wants something powerful, the browser usually asks you first, for that site only. You can turn it off later in settings. Phones do something similar for native apps now, but store apps still often ask for a long list, and ad kits can ride along. Seclusa asks for almost nothing.

Your browser gets the security patches

When Chrome or Firefox updates, the sandbox under every PWA gets those fixes. You are not waiting for every app maker to rebuild a store binary for that layer. The app’s own code still updates from the website when you are online — that is the next section’s worry.

Honest limits

A PWA is not magic. If an app phones home, tracks you, or asks for everything, the platform will not save you. Privacy comes from how the app is built: local data, no accounts, no trackers, open source you can read.

The big worry, simply

When you open a Seclusa app, your phone does not keep a sealed copy forever. It can ask the website “got any updates?” and download whatever that website sends.

If a bad person ever got control of that website — for example by taking over the GitHub login — they could send poisoned app code next time you are online. Your browser would run it, thinking it is still Seclusa.

That is the Privacy Guides point: with a normal website or PWA, you have to trust whoever controls the site every time it updates — not only the first time you installed it. For something like a crypto messenger, that worry is a really big deal. For notes and weather on your own device, it still matters, but the prize for an attacker is smaller.

What helps — and what does not

Seclusa apps are just static files on GitHub Pages. No fancy server. No database. No login cloud of your notes to steal. That makes the usual “hack the app server” path harder.

Open source means the code is public, so sneaky changes can show up in git. It does not mean “lots safer” by itself. Publishing the code only helps if someone actually looks. It does not stop a bad update from going live.

Static hosting also does not cancel the Privacy Guides worry. If someone controls the hosting account, they can still publish bad files. Security people treat that account like a signing key. A bad update can also stick a lasting service worker on your device until you clear it.

Short version: static + local + no accounts makes the worst case harder and less worth attacking. It is not “safe because static.”

GitHub 2FA — does it help?

Yes. A lot. Against “someone guessed or stole my password,” two-factor authentication is a big upgrade.

It does not make takeover impossible. Fake login pages can still trick some phone-app codes in real time. Stolen sessions or access tokens can push code without typing 2FA again. GitHub has warned about this and says hardware security keys are stronger than app codes for that.

CodeQL on GitHub — does it help?

I also run CodeQL code scanning on the GitHub repos. That is an automatic checker that looks through the source for known dangerous patterns (things like injection bugs and other common security mistakes).

It helps catch some accidents in code I write. It does not stop a stolen account from publishing bad files, and it will not catch every bug — only problems its rules know how to spot. Think of it as a seatbelt for coding mistakes, not a lock on the hosting account.

AI helpers and anyone who can push

I sometimes use AI coding tools (like Cursor) that can change files and, when I allow it, push to GitHub. Those tools sit inside the same trust line as a human with write access.

If bad code lands on main / GitHub Pages — because of a bug, a bad instruction, a compromised session, or me clicking “approve” without reading — that is the same class of failure as a stolen GitHub login: poisoned files on the live site. Mitigations that help: I approve pushes, I can read the diff, and open source leaves a public trail. The AI is not outside the threat model. It is one more hand that can publish.

Kill switch

If something ever looked wrong: clear the site’s data, remove the PWA, and only use it again after the real site is fixed. See also Clear-Site-Data.

Why Seclusa

Seclusa means private, secluded, set apart. I make these apps for myself and for anyone who wants useful tools without handing their life to a store profile or a sync server.

Everything here is open source on GitHub. Browse the app store, install what you need, and keep your data yours.
